# Note Guide

## note의 역할

note는 하나 이상의 session에서 검증된 지식만 뽑아 주제(기술/개념) 기준으로 정제한 자료다. 시행착오나 학습 과정이 아니라 "지금 확인된 결론"을 담는다.

## 기술 분야별 디렉터리 분류 기준

- 경로: `notes/<category>/<topic-slug>.md`
- `<category>`는 언어, 프레임워크, 도구, 개념 영역 등 기술 분야를 기준으로 정한다 (예: `java`, `git`, `system-design`).
- 기존 `notes/` 하위 디렉터리 목록을 먼저 확인하고, 이미 유사한 category가 있으면 새 category를 만들지 않고 재사용한다.
- category 이름은 소문자와 하이픈을 사용한다.

## 한 파일에 하나의 핵심 개념 원칙

- note 하나는 하나의 핵심 개념만 다룬다. 여러 개념을 한 파일에 묶지 않는다.
- 개념이 넓다면 하위 개념 단위로 파일을 나누고 "관련 개념" 섹션으로 서로 연결한다.

## 정의, 원리, 예제, 주의점 작성법

- **정의**: 한 문장으로, 다른 개념과 구분되는 핵심 특징이 드러나게 적는다.
- **핵심 원리**: 왜 그렇게 동작하는지, 내부적으로 무슨 일이 일어나는지 설명한다.
- **기본 예제**: 실제로 실행되고 검증된 최소 예제만 싣는다. session에서 동작이 확인되지 않은 코드는 그대로 옮기지 않는다.
- **주의점**: 흔한 오해, 실수, 예외 조건을 적는다.

## 관련 session과 기존 note를 먼저 찾는 절차

1. `notes/<category>/`에서 같은 주제 또는 인접 주제의 note가 있는지 확인한다.
2. `sessions/`에서 이 주제를 다룬 모든 session을 찾는다 (파일명과 본문 키워드 모두 확인).
3. 찾은 session을 모두 읽고 확인된 내용과 확인 필요 내용을 구분한다.

## 기존 note를 생성하지 않고 갱신해야 하는 기준

- 같은 핵심 개념을 다루는 note가 이미 존재하면 새 파일을 만들지 않고 그 note를 갱신한다.
- 다루는 개념이 명확히 다르면(같은 category라도) 새 note를 만든다.
- 애매한 경우 기존 note를 갱신하는 쪽을 기본값으로 한다 — 중복 파일보다 갱신이 우선이다.

## 상충하는 session 내용을 검증하는 방법

- 여러 session에서 같은 주제에 대해 다른 결론이 나왔다면 임의로 하나를 선택해 note에 반영하지 않는다.
- 최신 session의 결론을 우선 후보로 삼되, note에 "이전에는 A로 이해했으나 B로 정정됨" 형태로 정정 과정을 남긴다.
- 어느 쪽이 맞는지 판단할 근거가 부족하면 "검증 필요"로 표시하고 사용자에게 보고한다. 임의로 사실처럼 확정하지 않는다.

## 출처 session 상대 링크 규칙

- note의 "출처 session" 섹션에 이 note의 근거가 된 모든 session을 저장소 상대 경로로 나열한다 (예: `../../sessions/2026-08-20-java-sealed-class.md`, note 파일 기준 상대 경로).
- session이 추가로 근거가 되면 목록에 추가하고 기존 항목은 삭제하지 않는다.

## 참고 자료와 확인 날짜 작성 방법

- 외부 문서/공식 문서를 참고했다면 "참고 자료" 섹션에 URL과 확인 날짜(`YYYY-MM-DD`)를 함께 적는다.
- 확인 날짜가 없는 외부 링크는 추가하지 않는다.

## templates/note-template.md 사용법

- 새 note는 `templates/note-template.md`의 구조를 그대로 따른다.
- `{{TITLE}}`, `{{CATEGORY}}`, `{{DATE}}`를 실제 값으로 치환한다.
- note를 갱신할 때도 "마지막 검토일"을 갱신한 날짜로 업데이트한다.
